## Known Quirks

Confirmed live on Forge (`flux-fiqll6jza49.forge.zehntech.com`, 2026-08-21) via Playwright MCP exploration — real DOM, not guide assumptions:

- **New SLA form has no visible Project field**, contradicting `HELPDESK_USER_GUIDE.md` §3.2 ("leave blank for global"). Also has an undocumented **file-upload "SLA Agreement" field**. Confirmed real field ids: `#sla_response_time_unit`, `#sla_resolution_time_unit`, `#sla_working_hours_end` (start end has a matching `#sla_working_hours_start`-style id, not yet double-checked). **RESOLVED 2026-08-24 (corrects an earlier wrong guess that SLA is simply "a global, install-wide entity" — it is NOT that simple):** SLA project-scoping is real but invisible — driven by a hidden `<input type="hidden" name="project_id">` that only exists when the form is reached via `/rf_slas/new?project_id=X` (exactly the URL a project's own "New SLA" button under its Helpdesk SLA tab links to). Going to the bare `/rf_slas/new` (as this session did for both "Standard" and a throwaway "ProjectScopeTest1") creates an orphaned SLA with no project_id at all — it then shows in the global admin list at `/rf_slas` but in **no** project's own Helpdesk SLA tab. Confirmed by creating one SLA each way and checking both a project's SLA tab and a different project's SLA tab. Also confirmed: adding `?project_id=X` to the *global list* URL (`/rf_slas?project_id=X`) does nothing — it silently ignores the param and returns the unfiltered list; only the actual project-nav route `/projects/:id/helpdesk/sla` filters correctly. **Filed 2026-08-24 as BUG-HLP-005**: the global `/rf_slas` and `/rf_support_levels` list pages (unlinked from any discoverable nav) each have their own working "New" button pointing at the bare, unscoped `/new` route — so this isn't just a hand-typed-URL edge case, it's one click away once someone lands on either list page. Also newly confirmed: bare `/rf_support_levels/new` still has a required Project dropdown (so it doesn't orphan), but that dropdown lists every project on the instance, including ones without the Helpdesk module enabled at all. **RESOLVED 2026-08-24 (new Forge instance, `flux-fudbk2hlu49`):** the Customer form's SLA Name dropdown IS correctly scoped by the row's own Project selection, on both New and Edit — same mechanism as Support Level. Confirmed with two properly-scoped SLAs ("Standard"→Helpdesk Service Desk, "AgileSLA"→Agile Board Project) and two Support Levels ("L1"→Helpdesk Service Desk, "AB-L1"→Agile Board Project): selecting a Project in the row disables (does not remove) the other project's SLA/Support Level `<option>`, and switching Project resets the row's SLA/Support Level selection back to "none". Verified symmetric both directions and on the Edit form for an existing customer. The earlier "worth checking" note above was inconclusive because a superficial look at dropdown contents (options listed but `disabled`) can look identical to "no filtering" unless you check the `disabled` attribute specifically — not a bug, just an earlier incomplete check.

## Confirmed Working (addendum #5, 2026-08-25) — Internal Note vs. Reply Note, ticket #272

Direct follow-up test: does an **Internal Note** (the reply form's other radio option, alongside "Reply Note") carry the same side effects as a Reply Note? Tested live as `admin` on ticket #272 (Status: In Progress, Assignee: Redmine Admin at the time).

**Result: Internal Note has zero side effects — a clean, complete contrast with Reply Note.**

| | Reply Note | Internal Note |
|---|---|---|
| Assignee | Reassigns to whoever submits it | **Unchanged** |
| Status | Forces → "Waiting for Customer Response" | **Unchanged** (stayed "In Progress") |
| SLA pause/recalculation | Triggers it (deadlines shift, pause timestamp resets) | **None at all** — "Paused since" timestamp, both deadlines, and the Activity Log (still exactly 2 events) were all byte-for-byte identical before and after |
| Where the text appears | Only in the "Helpdesk Conversion" (outbound email) tab — never inline on the main issue view | Shown directly inline on the main issue page, marked "Private" |
| "Helpdesk Conversion (N)" count | Increments | **Does not increment** — correctly excluded from the customer-facing email trail |
| New tab that appears | — | A **"Notes" tab** appears in the tab bar for the first time once any Internal Note exists (History / Notes / Property changes / Helpdesk Conversion / SLA Information) — not present when only Reply Notes exist |

This confirms Internal Note is a genuine, isolated "agent-only comment" — safe to use for scratch/coordination notes without disturbing the ticket's customer-facing state, Assignee, or SLA tracking in any way. Not yet covered by any test case in `HELPDESK_TICKET_LIFECYCLE.md` or `HELPDESK_SLA_ESCALATION.md`.

## Recurring Issues (addendum, 2026-08-25) — SLA lifecycle deep-dive, ticket #272

User asked to manually test one flow end-to-end: customer creates a ticket → an agent logs in and replies → does the ticket auto-assign to that agent, and does the SLA clock start? Executed live on `flux-fwdq7ydhw49` with real fixtures (customer `acme.hd.contact`, agent `daisy.skye`, ticket #272, "Standard SLA"/L1 on Helpdesk Service Desk). Findings, confirmed step by step:

- **Reply auto-assigns and auto-transitions status** — with zero manual assignment, saving a Reply Note as `daisy.skye` immediately set Assignee → Daisy Skye and Status: New → "Waiting for Customer Response". Confirmed via the ticket's own History tab ("Assignee set to Daisy Skye", "Status changed from New to Waiting for Customer Response").
- **SLA does not exist on a ticket until an agent's first action** — before the reply, ticket #272 showed "No SLA" everywhere (ticket list's SLA Status column, no "SLA Information" tab at all), *despite* the customer's organization (Acme Corp) having Standard SLA correctly configured in Project Access. This matches every other pre-existing ticket on this instance (#227–271), all showing "— No SLA" regardless of customer/org.
- **The reply is what starts the SLA, and immediately IS the First Response** — the moment the reply saved, a new "SLA Information" tab appeared showing: SLA Started at the exact reply timestamp, "✓ Responded" (First Response) logged at that same timestamp, a Response deadline, and a Resolution deadline — all computed from that one action.
- **Deadlines are working-hours-aware, not wall-clock** — reply landed at 07:27 AM UTC (before Standard SLA's 09:00–18:00 Mon–Fri window). Computed First Response deadline was 01:00 PM UTC same day; computed Resolution deadline was 08/27 03:00 PM UTC. Both figures only reconcile if the clock started counting from 09:00 AM (the window's start), not 07:27 AM — hand-verified: 09:00 + 4h (Standard SLA's First Response Time) = 13:00 = 1:00 PM ✓; 24h of business-hours (9h/day, Mon–Fri) from Tue 09:00 lands exactly on Thu 08/27 15:00 ✓.
- **The reply also immediately PAUSES the SLA** — because it set Status to "Waiting for Customer Response", the SLA Information tab shows "⏸ Paused — the clock is not running. Paused since [reply timestamp]" from the very same moment it started. Makes sense in principle (don't count resolution time against the agent while waiting on the customer) — see below for why the pause turned out to be a bigger problem than expected.
- **A rich SLA Information UI exists, fully undocumented anywhere** (`HELPDESK_REQUIREMENTS.md`/`HELPDESK_USER_GUIDE.md`/`HELPDESK_SLA_ESCALATION.md` don't mention any of this): an "SLA Overview" table (Organization/SLA Policy/Support Level/SLA Started/Initially Assigned To/Current Assignee), an "SLA Journey" table (per-escalation-stage: Stage/Support Level/Agent/Active Period/Response SLA/Resolution SLA/Escalation Trigger — currently 1 stage, "Initial Stage ● Current"), and an "Activity Log" table (timestamped events: "▶ SLA Started", "✓ First Response Given", etc.). None of this exists in any test case file yet.
- **CRITICAL follow-up finding — the pause may never be resumable through the UI at all.** Tried to simulate "customer responds" (since the real customer literally cannot — see BUG-HLP-006, re-confirmed blocked again this session even in this exact "Waiting for Customer Response" status) by manually changing Status via Edit from "Waiting for Customer Response" → "In Progress" as `daisy.skye`. Result: **the SLA stayed paused at the identical original timestamp** — no new Activity Log entry, no visible change to the pause state at all. Checked the ticket's "Actions" menu (only had "Copy link", nothing SLA-related) and the "Helpdesk Conversion" tab (confirmed this is an OUTBOUND email-notification log — the note that got emailed to the customer — not an inbound reply channel) for any other resume mechanism; found none.
  - **Combined implication**: if resuming the Resolution SLA requires an actual customer reply (not just any agent-side status change), and the customer is structurally blocked from ever replying (BUG-HLP-006), then **the Resolution SLA becomes permanently frozen the moment any ticket gets its first agent reply** — a much larger consequence than BUG-HLP-006's original "customer can't follow their ticket" framing. This compounds two behaviors into something that may block the plugin's core resolution-tracking promise entirely, not just the customer self-service UX.
  - **Not yet tested**: whether an inbound EMAIL reply (Helpdesk Settings has an "Email Configuration" tab, never exercised end-to-end this engagement) is the intended/working resume path instead of a web-UI action. This is the key open question before deciding whether this is a new bug, a symptom of BUG-HLP-006, or working-as-designed with email as the only valid channel.
  - **Explicitly not filed as a bug yet** (2026-08-25) — user chose to just document this and decide later, pending the email-reply-path question above.
  - **CORRECTION, same session, immediately after:** a second **Reply Note** (submitted by a different user, `admin`, with trivial text "test") DID trigger a real recalculation — "Paused since" moved from 07:27 AM to 07:36 AM, and BOTH the Response deadline (01:00 PM → 01:08 PM) and Resolution deadline (Aug 27 03:00 PM → 03:08 PM) shifted forward by the exact real-world elapsed time since the SLA started. So the resume/recalculation mechanism is real and does work — but it is gated specifically behind an actual **Reply Note** action (from ANY user, not just the original assignee — this reply also reassigned the ticket from Daisy Skye to `admin`), never behind a bare Status field edit via the Edit form (confirmed again: my earlier manual Edit-form status change produced no recalculation at all). **Revised conclusion: the Resolution SLA is not "permanently frozen" — it's only resumable by an agent's Reply, never by the customer's** (who still can't reply at all, per BUG-HLP-006). Less severe than first reported, but the underlying UX problem (customer can never genuinely close the loop) stands. Also newly noted: the SLA Overview table's "Current Assignee" column stayed "Daisy Skye" even after the ticket's real Assignee changed to `admin` — appears stale/not live-updated, a minor separate observation.
  - **Follow-up, same session — Internal Note tested as the cleaner alternative**: confirmed an **Internal Note** (as opposed to Reply Note) has zero effect on Assignee, Status, or SLA state at all — see the "Confirmed Working (addendum #5)" entry above for the full comparison table.
