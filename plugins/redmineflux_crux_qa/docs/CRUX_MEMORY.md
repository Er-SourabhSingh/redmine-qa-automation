## Standing instruction — cost efficiency (2026-10-26, explicit user request)

While testing Ask Crux chat (any agent), watch for **redundant/excessive tool calls or multiple LLM round-trips for a single request** — this is a real, reportable cost-inefficiency defect in its own right, not just a side note, since every round-trip is billed against a shared, limited OpenRouter balance. Already-known instances of this pattern: **BUG-CRX-060** (5-6 LLM round-trips of tool-group discovery per turn before a token-budget cutoff, never reaching the real write tool) and **BUG-CRX-065** (10 wasted tool calls fetching issues one at a time instead of the one purpose-built list tool). When a *new* instance is found (a request that should be cheap but burns many calls/generations), file it as its own bug with the real `tool_calls`/generation count and cost pulled from `docker compose logs crux-core | grep cost_usd`, not just mentioned in passing.

At the end of any session that used Ask Crux chat, report the real aggregate OpenRouter spend, broken down per chat session — compute it from the logs (`docker compose logs crux-core | grep cost_usd`, summed by `[ses:...]`), never estimate it. On 2026-10-26's session: ~$1.33 total across 28 chats/166 generations.

## Known Quirks

- **2026-10-27 — Redmine Testcase Management's "Create test suite"/"Create/manage test suites" visibility is gated by `view_test_suite` SEPARATELY from `create_test_suite`/`edit_test_suite`/`delete_test_suite`.** When building the "QA Full Access" role fixture, all 3 CRUD permissions were granted but `view_test_suite` itself was missed — the role could genuinely create/edit/delete suites via the API, but Crux's `edit_test_suite` chat path still honestly refused with "I don't have permission to view or manage test suites... grant the `view_test_suite` permission" until that box was also checked. This was a fixture-setup gap, not a Crux bug — verified via DB that `view_test_suite` was genuinely absent before the fix and genuinely present after. **When granting "full" Testcase Management permissions to a role, always check `view_test_suite` explicitly** — it's easy to assume the 3 CRUD checkboxes imply it, but they don't.
- **2026-10-26 — creating a project via native UI with Playwright's `fill()` on the Name field alone silently fails if the Identifier field is left blank.** Redmine's own JS auto-slugs the Identifier from Name as you type (listening for real keystroke/input events), but Playwright's `fill()` sets the value directly without firing those events, so Identifier stays empty — and `ProjectsController#create` then re-renders the `new` form (`200 OK`, no redirect) instead of creating the project, with no error visibly surfaced in a quick glance (the validation message is there but easy to miss if you don't check the response status/redirect). **Always explicitly fill both the Name and Identifier fields** when creating a project this way — don't rely on the auto-slug. A `200 OK` landing back on `/projects/new` (rather than a redirect to `/projects/<identifier>/settings`) is the tell that this happened; verify a just-created project genuinely exists via DB/URL before building further fixtures on top of it.
- **2026-10-26 — this stack (`C:\crux-redmine`) never had a Redis/Sidekiq service — the Testcase Management plugin's own Configuration page save ("Apply") 500s on `RedisClient::CannotConnectError` because Sidekiq defaults to `redis://localhost:6379` with nothing listening there.** Not a plugin or Crux bug — a genuine missing infrastructure piece on this environment, same class as the earlier `CRUX_DISCOVERY_WRITE_GROUPS`/Document-Category/Approved-Hours gaps. **Fixed by adding a `redis` service** (`redis:7-alpine`, standard healthcheck) to `docker-compose.yml`, making `redmine` `depends_on` it, and setting `REDIS_URL: redis://redis:6379/0` on the `redmine` service's environment (pattern copied from the plugin's own reference `docker/docker-compose.demo.yml`). After `docker compose up -d redis && docker compose up -d redmine`, the plugin Configuration page saves cleanly (verified via DB: `settings.value` for `plugin_redmineflux_testcase_management` shows `tracker`/`defected_tracker`/`feature_tracker` genuinely persisted, no more `:empty: true`). `docker-compose.yml` here is **not** version-controlled (no `.git` in `C:\crux-redmine`), so this fix only lives on-disk — re-apply it (or keep a copy of the diff) if the stack is ever rebuilt from a fresh clone/template. Worth checking whether other plugins (Timesheet's scheduled reminders, etc.) were also silently degrading before this fix, since they share the same Sidekiq/Redis dependency.

- **2026-10-11 — Redmine 6's role edit page scopes `view_issues`/`add_issues`/`edit_issues`/`add_issue_notes`/`delete_issues` PER-TRACKER via a second, separate grid further down `/roles/<id>/edit` — checking the top-level permission checkbox alone does NOT grant the permission.** Found while setting up TC-CRX-189: checked "View Issues" on the Manager role's top checkbox list and saved; `allowed_to?(:view_issues, project)` correctly returned `true`, but `Issue#visible?` still returned `false` and the native UI still gave a real 403 for the test user. Root cause (confirmed via `Issue.visible_condition` SQL and `role.settings`): these 5 permissions ALSO require a tracker to be checked in a "Tracker × Permission" table rendered below the main checkbox list (a "All trackers" row, plus one row per tracker) — the role's `settings['permissions_all_trackers']`/`['permissions_tracker_ids']` hash defaults every one of these 5 permissions to **zero trackers granted** even when the plain top checkbox is checked. **Fix: also check "All trackers" (or specific trackers) in that lower grid for each of the 5 scoped permissions, then Save** — verify with `Issue.find(<id>).visible?(user)` or a real native-UI page load, not just `allowed_to?`, since `allowed_to?` alone does NOT reflect this tracker-scoping gap. **Apply this to TC-CRX-190/191/192 too** (`add_issues`, `edit_issues`, `delete_issues` are all in the same scoped-permission list) — grant both the top checkbox AND the tracker grid's "All trackers" cell for each, or the "with permission" half of those TCs will falsely still show a refusal/403 that looks like a Crux bug but is actually incomplete fixture setup.

- **2026-10-11 — ALWAYS check `tools/list`'s reported count in `docker logs crux-redmine6-crux-core-1` before trusting any "this isn't available"/"couldn't confirm available" response from Crux on this stack.** If `mcp-1` starts before Redmine is reachable (its own startup self-test retries for ~120s/27 attempts then gives up), it permanently falls back to a degraded ~95-100 tool catalog with **0/14 plugins detected**, and never retries even after Redmine becomes healthy — only a manual `docker restart crux-redmine6-mcp-1` (with Redmine already up) fixes it, recovering to the full ~495-498 tools / 13-14 plugins. This happened on a normal session start on 2026-10-11 (filed as **BUG-CRX-063**) and would make every plugin-domain capability look falsely unavailable if not caught. **Standing session-start check**: `docker logs crux-redmine6-crux-core-1 --since 5m 2>&1 | grep "tools/list"` — if it shows `tools=95` (or anything well under ~495), restart `mcp-1` before trusting any capability-denial finding.

- **2026-10-10 — time logging (any method: issue-edit "Log time" sub-form, or dedicated `/issues/<id>/time_entries/new`) requires TWO preconditions or it fails with "Category can not be blank" and NO visible Category field anywhere on the time-entry form to fix it.** Confirmed via direct user guidance, not a bug: (1) the project must have at least one **Approved Hours** entry set (Settings → Approved hours → "Add Approve Hours", picking an Hours amount + a Category + a Comment), AND (2) the **issue itself** must have its own Category field set to a category that has approved hours. Without both, every time-log attempt fails silently-ish (a real validation error appears, but it names a field that isn't rendered on the form, so it looks like a dead end). **Also confirmed: setting the issue's Category and logging time in the SAME form submission (the issue edit page's combined "Change properties" + "Log time" sections) still fails** with the same "Category can not be blank" error even though the Category dropdown shows the just-submitted value selected — the two must be two separate requests (save Category first via a status-only/category-only Submit, confirm it persisted, THEN log time via a second submit). This is almost certainly the Budget Audit / Approved Hours plugin's time-entry validation running before the issue's category update has committed within the same request — a real ordering quirk, not something to treat as a reproducible "bug" worth filing, but worth knowing before ever seeding time-entry test data on a fresh project.

- **2026-10-26 — `docker compose restart redmine` can crash-loop after a plugin code pull if two plugins' Gemfiles pin the same gem with different literal version-constraint strings.** `redmineflux_helpdesk` pins `connection_pool, '~> 2.4'`, `redmineflux_testcase_management` pins `connection_pool, '< 3'` — both ranges overlap (2.4.x satisfies `< 3`) but Bundler's duplicate-gem check compares the literal strings, not resolved ranges, and refuses to boot at all (`You cannot specify the same gem twice with different version requirements`). This blocks the ENTIRE Redmine container, not just one plugin. A message describing this was drafted for the dev; **a temporary local fix (aligning both Gemfiles to the same string) can get the stack running again, but must be reverted before ending the session** — don't leave it in place, since the real fix belongs upstream and a reverted file means the next restart will crash again until the dev ships it.
- **2026-10-26 — separately, `redmineflux_testcase_management`'s `config/initializers/grover.rb` unconditionally shells out to `` `npx puppeteer executablePath` `` at boot with zero error handling.** If `npx`/Node isn't installed in the image (it isn't on the official `redmine:6.0-bookworm` image), this raises `Errno::ENOENT` and crashes the ENTIRE app boot (not just a warning), even though the surrounding code already has a documented graceful-degradation path (falls back to HTML instead of PDF reports) for exactly this situation — the crash happens before that fallback logic ever runs. **Workaround that avoids touching plugin code**: set `PUPPETEER_EXECUTABLE_PATH` in `docker-compose.yml`'s `redmine` service environment to any placeholder string (e.g. `/usr/bin/chromium-placeholder`) — the initializer's `ENV['PUPPETEER_EXECUTABLE_PATH'] || \`npx ...\`` short-circuits the backtick call entirely, and the already-written `pdf_generation_available?` check then correctly logs a warning and degrades instead of crashing. Revert this env var after confirming the boot succeeds, for the same reason as the Gemfile fix above.
- **2026-10-26 — Timesheet weekly/teams native UI pages require a non-null TEAM-role override on the `rf_team_memberships` row, not just a real Redmine project role, to pass the `authorize_team_mode_view_access!` filter.** A user who is a genuine Redmine project member with `view_timesheets` (e.g. Developer role) still gets a real 403 on `/timesheets/weekly` if their row in `rf_team_memberships` has `role_id = NULL` (the "None" option in the Teams page's Add/Edit Member UI) — the filter checks the team-membership role's own permissions, not the user's actual Redmine role. Setting the team-membership role explicitly (e.g. Reporter) if the targeted schema doesn't grant that role any approval level is the correct way to create a genuine "team member who cannot approve" fixture — don't leave it at "None" expecting the real Redmine role to carry over.
- **2026-10-26 — logging time via the issue-edit "Log time" sub-form silently re-renders the form (HTTP 200, no visible error) if the Activity dropdown is left at "--- Please select ---".** This is a distinct, simpler failure mode from the already-documented Approved-Hours/Category precondition gotcha above — don't assume every "time entry didn't persist" case is the Approved-Hours issue; check the Rails log for a plain `Completed 200 OK` with no `Redirected to...` line (the tell that validation failed and the form was simply re-rendered) and verify the Activity field was actually selected before assuming anything more exotic is wrong.
- **2026-10-26 — Version creation via native UI requires BOTH Start Date AND Due date (both marked `*` required) or it fails silently with no visible error, same "looks fine but didn't persist" shape as the Document Category / Approved Hours gotchas above.** Created a version "v1.0" leaving both date fields blank — the form submitted, the browser redirected to the versions index (looked successful), but `SELECT * FROM versions` showed 0 rows. Root-caused via Rails log: the `create` POST rendered the layout template directly instead of logging a `Redirected to...` line, the tell that a validation error occurred (the error itself wasn't visible because the re-rendered page apparently didn't retain focus/visible flash in this check). Re-submitted with both dates filled (`Start Date: 2026-10-26`, `Due date: 2026-12-31`) — redirected to `/settings/versions` (the real success path) and confirmed via DB. **Always fill both date fields when seeding a version fixture for this or any Crux suite, and always DB/UI-verify a just-created fixture before relying on it in a chat test** — this one silent-failure nearly caused a false "Crux falsely claims no versions exist" bug to be filed (the claim was actually true at the time, because of this setup mistake, not a Crux defect).

- **Misleading "✓"-prefix-on-genuine-failure pattern (BUG-CRX-018) is also systemic — now confirmed across 4 domain agents and 4 distinct failure types.** Originally found on the Capacity/Workload Agent (404 "allocation not found"), it has since reproduced identically on: a Workload team-create admin-permission denial, a Sales/CRM Forbidden (403) authorship-rule refusal, a KB Agent `manage_knowledgebase_pages` permission refusal, and a Scrum Agent core `Edit issues` permission refusal. Every one of these is a real, correctly-refused write — only the success-styled "✓" prefix is wrong. Confirms this is a single shared frontend/backend component unconditionally prefixing outcome text with "✓" regardless of whether the underlying `execute()` call actually succeeded, not an agent-by-agent bug.
  - **2026-10-11 refinement, Project Manager specifically (BUG-CRX-054): this ✓-mislabel is isolated to `create_issue`'s own error-rendering path, NOT shared by `update_issue`/`delete_issue` on the same agent.** Deliberately tested all 6 cells of a closed/archived × Create/Update/Delete matrix on the same two fixture projects: Create failed with the misleading ✓ on BOTH closed and archived (2/2, word-for-word identical template, only the project identifier differs — proves it's keyed to "project inaccessible for writes," not to closed specifically). Update and Delete failed on all 4 remaining cells too (expected — permission is genuinely denied either way) but rendered **honest red failure text with no checkmark** every time. **Testing technique worth reusing**: when a ✓-mislabel bug is found on one write tool for one agent, don't assume sibling write tools (Update/Delete/etc.) on the *same* agent share the same rendering defect — test them explicitly; this session found they did not.

- **False capability-denial pattern ("I don't have X tools available in this deployment") is a distinct, recurring fabrication shape — now confirmed post-2026-09-25-fix on 3 domain agents.** BUG-CRX-029 (QA Agent, fixed 2026-09-25) was the first documented instance. Two fresh instances appeared in the *same* retest sweep, at the exact trigger point where BUG-CRX-029's specific shape was just confirmed fixed: BUG-CRX-032 (Sales Agent, falsely denies CRM tools right after using them) and BUG-CRX-034 (Capacity Agent, falsely denies `team_create`/`member_remove`/`member_update` — objectively contradicted by `docker logs crux-redmine-docker-mcp-1` showing all 64 workload tools genuinely registered). Fixing one agent's instance of this pattern does not fix the underlying per-turn tool-discovery mechanism — check for this shape specifically (not just the zero-button/fabricated-success shapes) whenever retesting any domain agent's write path. **2026-10-09, new instance on the Redmine 6 build: Project Manager falsely claimed `redmineflux_core_list_custom_fields` doesn't exist** (BUG-CRX-050) — same shape, 4th confirmed agent, new domain (custom field introspection).

- **Wrong/hallucinated-ID resolution pattern (BUG-CRX-015/019/038/043 shape — never guess a numeric id from a name) now confirmed for custom fields too, not just users/teams/projects.** 2026-10-09, Project Manager (BUG-CRX-050): asked to set two named custom fields ("Text required feild" real id 4, "list required feilds" real id 5), the agent's confirm card instead targeted id 1 (a different real field, "Crux Capability") and id 45 (nonexistent on this instance) — both target fields ended up still blank on Redmine's validation error, while an unrelated field was wrongly targeted. - **2026-10-09 — same wrong-ID-resolution pattern confirmed on CORE issue fields too (Priority, Category, Target Version), with two new, more severe sub-shapes — BUG-CRX-052.** A single 11-field create_issue request (every standard issue-form field named explicitly) got 8/11 fields right but 3 wrong, each a different failure mode worth checking for separately in future field-resolution testing:
  1. **Had the correct reference data and still picked wrong** — `list_priorities` was genuinely called and returned the real list, yet the agent still proposed "Urgent" when the user said "High." This is NOT a missing-lookup problem like the others; it's a plain selection/misread error, and it's the most dangerous shape because the wrong value ("Urgent") is itself valid, so nothing in the write path catches it — it would have silently succeeded.
  2. **Used an ID its own tool had just called invalid** — `get_version` 404'd with an explicit "Version/milestone #1 not found," and the agent proposed `Fixed Version: 1` anyway in the very same turn. Worse than simply never checking — this is ignoring a just-received negative result.
  3. **Real list-then-match tool never called at all** — `list_issue_categories` (the tool that would show the real 14 categories) was never invoked; only a single-record `get_issue_category` guess, which fetched the wrong category entirely.
  Contrast: in this SAME request, Assignee (via `list_users`/`get_user`) and Tracker (via `list_trackers`) both resolved correctly — proving the agent CAN do real list-then-match resolution when it actually does it; the failures are case-by-case, not a blanket incapacity. **When testing any create/update with named enum-like fields (priority, category, version, tracker, custom fields, users), check the Activity Log for whether the matching `list_*` tool was actually called and whether its result was actually honored — a correct-looking confirm-card value is not proof the resolution was real.**
  **Even more severe follow-up, same bug**: re-sent the identical request with the 3 broken fields (Priority/Category/Version) removed entirely — Priority was not mentioned anywhere in the new message. The confirm card still showed `Priority: Urgent`, carried over from the earlier (Cancelled) proposal's wrong value. With nothing else to conflict this time, **Confirm genuinely succeeded and wrote Urgent to a real issue (#7)** — a stale value from a cancelled, unrelated-field-wise proposal leaked across turns into a later proposal that never asked for it, with zero validation catching it. **New testing technique worth reusing**: after finding any wrong-field-resolution bug, don't just retry with the bad field removed and call it done if the card "looks clean" — explicitly re-check every OTHER field in the new card too, since a prior turn's bad value can silently reappear uninvited.
  **Third, independent, user-driven reproduction — rules out session-leak as the sole cause.** A completely fresh chat (zero prior turns) with "create issue subject hello world priority high" → the agent's OWN clarifying-question reply correctly restated "priority High" in plain text, then the final confirm card still showed `Priority: Urgent`. **3/3 reproductions now, all the identical High→Urgent substitution, never any other priority pair** — this is not random LLM noise or purely a cross-turn leak, it looks like a specific, deterministic mis-mapping (worth checking whether the priority list's real ordering/id scheme has High/Urgent adjacent and there's an off-by-one somewhere in how a matched name becomes the rendered value).
