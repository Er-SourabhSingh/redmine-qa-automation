## Findings surfaced during authoring (triage before filing)

1. **`TestcasesController` does not exist anywhere in this codebase**, yet `config/routes.rb`
   routes a large surface to it: the full `resources :testcases`, `resources :testcase_steps`,
   plus the named routes `PUT /update_testcases`, `POST /copy_test_case`,
   `PATCH edit_testcase_path`, `PUT update_assignee`, `DELETE testcase_steps/:id`, and
   `DELETE testcase (as: delete_testcase)`. Two of these are actively wired to real UI: the
   single-row drag-and-drop "Copy Testcase"/"Move Testcase" popup in
   `app/views/issue_testcase/new.html.erb` calls `copyTestcase()`/`moveTestcase()`
   (`assets/javascripts/testcase.js`), which POST/PUT to `/copy_test_case.json` and
   `/update_testcases.json`. Hitting any of these raises `uninitialized constant
   TestcasesController`. The working equivalents live on other controllers: cloning/moving via
   checkbox multi-select goes through `TestSuitesController#copy_issues`/`#add_issues`; step
   delete goes through `StepsController#destroy`; case delete/edit/assign go through core
   Redmine Issue actions. (Surfaced by TC-CASE-03-03, TC-CASE-05-01.)
2. **`case_statuses_controller.rb` and `case_priority_controller.rb` also don't exist**, despite
   `resources :case_priority`, `resources :case_statuses`, `PUT /update_priority/:id`, and
   `PUT /update_testcase_status/:id` all being routed. There is no admin Settings partial for
   case statuses/priorities either (`app/views/settings/` has no `_case_statuses` partial). The
   only functioning CRUD is the MCP JSON API. README's "Administrators: Custom case priorities,
   statuses, and run statuses" feature claim has no browser UI behind it for statuses/priorities
   today. (Surfaced grounding F-CASE-07.)
3. **`IssueTestcaseController#fetch_testcases`** (routed at `GET /fetch_testcases`) references
   `Testcase.where(id: testcase_ids)` — there is no `Testcase` model anywhere in `app/models`
   (only `Issue`, which is what test cases actually are). Calling this action would raise
   `NameError: uninitialized constant Testcase`.
4. **`assign_requirement` is documented against `add_requirement` but enforced against
   `edit_test_suite`.** README's Permissions table lists `add_requirement` ("Link requirements
   to test cases", recommended for "QA Lead, Business Analyst") as the relevant permission, but
   `POST requirement_issues/assign_requirement` → `TestSuitesController#assign_requirement` is
   gated by `rftc_authorize_suite_record`, which checks **`:edit_test_suite`**, not
   `:add_requirement`. A Business Analyst granted exactly what the README recommends
   (`add_requirement` only) would be denied by the actual code.
5. **`copy_issues_to_test_suite` does not validate the target suite's project.** The duplicated
   Issue keeps the *original* issue's `project_id` (via `Issue#copy_from`), while the new
   `IssueTestSuite` row links it to whatever suite id was passed — including a suite belonging
   to a different project (`Testsuite.project_id` is a free-standing identifier string, never
   cross-checked against the copied issue's project here). This can produce a test case that is
   organizationally "in" one project's suite tree while its underlying Issue still belongs to
   another project.
6. **Test suite delete is run-guarded; test case delete is not.** `TestSuitesController#destroy`
   explicitly blocks deletion when the suite (or any descendant) has runs attached
   (`error_testsuite_associated`/`error_testsuite_subfolders`). The equivalent for an individual
   test case does not exist — `issue_patch.rb` declares `has_many :run_issues, dependent:
   :destroy`, so deleting a test case that is currently part of an open run cascades silently
   with no warning. Worth a product decision on whether this asymmetry is intentional.

## Findings surfaced during authoring (triage before filing)

1. **Defect-on-failure enforcement is under-documented in `API.md`.** The hard requirement that
   Failed/Blocked results need `defect_ids` (enforced identically in both `create` and `bulk_create`
   via `CaseStatus#requires_defect_link?`) appears only as a single "Important:" sentence under
   endpoint 18 (Create Status Result) and is **not repeated** under endpoint 19 (Bulk Create Status
   Results), even though the code enforces it identically there. A CI integrator reading only the
   bulk-create section could reasonably miss this. Recommend adding the same callout to endpoint 19.
2. **`API.md`'s stated auth scheme (HTTP Basic, line 5-15) does not match the header actually used
   elsewhere in this catalog and in the real controllers** (`X-Redmine-API-Key` / `?key=`, via Redmine's
   standard `accept_api_auth`). Both mechanisms are valid Redmine API auth, and the code does not
   restrict to Basic only, but the doc's blanket "Authentication is HTTP Basic Auth on every endpoint"
   statement is misleading for integrators who will reach for the API-key header first. Recommend
   clarifying that both are accepted.
3. **Single `create` vs. `bulk_create` diverge on TWO axes, not one, and only one is explicitly
   documented.** The seeded-Untested transition-in-place behavior (rftc-009) is implemented ONLY in
   `bulk_create`; the single-record `create` endpoint always inserts a new row, even against a fresh
   seeded Untested cell (see TC-EXEC-05-04). Separately, `bulk_create` is per-row partial-commit while
   rftc-008's `link_defect`/`bulk_link` is deliberately all-or-nothing (TC-EXEC-02-02 vs.
   TC-DEFECT-03-02). Neither divergence is stated in `API.md`'s endpoint-18/19 text; both are
   intentional per the source comments, but worth a documentation pass so integrators do not assume
   endpoint-18 and endpoint-19 behave identically w.r.t. seeded rows.
4. **`RunType#belongs_to :run_type` wiring is thin.** `RunType` itself has `belongs_to :run, optional:
   true` (the reverse of what the name suggests — a `RunType` belongs to a `Run`, not the other way
   round) and `Run belongs_to :run_type`. The settings-page CRUD (`RunTypesController`) never
   references `run_id`, so it is unclear from the controller alone how/whether `run_type_id` actually
   gets set on a `Run` through the New Run form (`@run_types = RunType.where(is_enabled: true)` is
   loaded into `new`, but no `run.run_type_id` assignment is visible in `RunsController#create`/
   `#update`). TC-RUN-02-04 is written defensively around this; recommend a developer confirms whether
   Run Type selection is actually wired end-to-end or is a configured-but-unused field, and files a
   defect if the latter.
5. **No explicit batch-size ceiling on `bulk_create`'s `issue_status_results` array**, unlike
   `link_defect`'s documented `MAX_BULK = 500`. TC-EXEC-02-07 is exploratory for this reason — it is
   plausible this is intentional (CI builds can be large) but worth confirming it is not an
   oversight, since rftc-008's own spec text explicitly calls `bulk_create`'s cap "the shared bound" it
   is matching, implying one was assumed to exist.
6. **rftc-008's own Open Questions (not yet resolved per the planning doc) directly affect this
   catalog's long-term validity:** (a) the `defect_ids` CSV is explicitly planned for retirement in a
   follow-up **rftc-010** — once that ships, any test case here that asserts on the CSV directly
   (TC-DEFECT-01-01, TC-DEFECT-02-01/02, TC-DEFECT-05-01/02) will need updating to assert on the join
   only; (b) `report_defect` (MCP controller) is **not yet refactored** to call `ExecutionDefects::Linker`
   directly — it still writes the CSV and relies on the `after_save` reconcile hook, which TC-DEFECT-05-01
   effectively exercises as a regression guard for that gap.

## Findings surfaced during authoring (triage before filing)

- **F-PERM-04 / milestone status codes depend on project visibility, not just membership.** Reads gate on
  `project.visible?`, which on a PUBLIC project returns `true` for any logged-in user regardless of TCM
  module permissions — so a milestone-list IDOR case only proves denial when the target project is
  genuinely private. If `alpha-web` is configured as a public demo project, TC-PERM-04-2's read-deny steps
  (2) will pass through as 200, not 404 — that is CORRECT behavior per the code (`rftc_require_project_visible!`
  is a weaker, intentionally-visibility-only gate for endpoints with no dedicated view permission), not a
  regression. Confirm `alpha-web`'s actual visibility setting before treating a 200 on those reads as a bug.
- **F-SAFE-07's residual is intentionally asymmetric with F-PERM's "deny by default" posture.** The six
  remaining API-key-in-URL views are a genuine, currently-live weakness (URL/log/Referer exposure) that the
  team has explicitly chosen to ship with, tracked for a named follow-up — this is the one place in this
  catalog where "it still does the unsafe thing" is the PASS condition for TC-SAFE-07-2, which is
  easy to misread as a failure if the tester isn't told in advance. Keep the two email-template-adjacent
  partials (now fixed, TC-SAFE-07-1) clearly separated from the six-view residual (TC-SAFE-07-2) in any
  report so a reviewer doesn't conflate "partially fixed" with "not fixed."
- **`issue_status_results_controller.rb` has two more assignee-adjacent guards (lines ~373, ~417) beyond
  `create`/`bulk_create`** (`unless User.current.admin? || User.current.allowed_to?(:execute_testcase, @project)`)
  that were not individually itemized as their own F-PERM feature in this catalog's scope but share the
  exact C4 pattern. If a future pass adds dedicated actions here (e.g. a defect-linking endpoint), reuse
  TC-PERM-05-1's structure rather than writing a new pattern from scratch.

## Findings surfaced during authoring (triage before filing)

1. **API.md Authentication section is stale (Basic-Auth-vs-API-key drift).** `API.md:1-16` states
   "Authentication is HTTP Basic Auth on every endpoint" with ONLY the `Authorization: Basic
   <base64(...)>` form documented as required on all endpoints. The actual routes/controllers
   (`swagger_projects_controller.rb#require_basic_auth`, every `apis/mcp_*` controller's
   `accept_api_auth` call, and `API.md`'s own CI Bootstrap Run entry at line 1137) accept a Redmine
   API key via header, query param, **or** Basic-with-key-as-username — the form used everywhere else
   in the product. This is a documentation accuracy bug in `API.md`'s top section, not a code bug;
   recommend fixing the Authentication section to describe all three accepted forms (matching the CI
   Bootstrap Run entry's own `**Auth**` line, which already states it correctly) rather than changing
   any test or code to Basic-only.
2. **Plugin version mismatch: `init.rb` says 7.1.0, `README.md`/`CLAUDE.md` compatibility tables say
   7.0.0.** `init.rb:79` declares `version '7.1.0'`; `README.md`'s Installation table (lines 134-138)
   and `CLAUDE.md`'s Redmine Compatibility table (lines 21-26) both list **Plugin Version: 7.0.0** for
   all three majors. Either the docs were not bumped on the last version bump, or `init.rb` was bumped
   ahead of a doc-sync step. TC-COMPAT-01-04 exists specifically to check whether this drift is
   doc-only or has also leaked into a customer-visible UI string.
3. **Bulk status-result partial-failure atomicity is undocumented.** `API.md`'s 422 example for
   `bulk_create` (line 1010-1019) shows an `errors` array for the invalid rows but does not state
   whether the valid rows in the same batch commit or the whole batch rolls back. TC-API-04-04 is
   written to observe and record the actual behavior rather than assume either outcome — flag as a
   doc gap regardless of which way it behaves.
4. **`view_test_suite` permission only recently became grantable (BUG-CRX-024, see `init.rb:85-98`
   comment).** Before that fix, no role could ever be granted it, silently blocking the dedicated
   `list_test_suites`/`get_test_suite` MCP endpoints for every non-admin. TC-API-07-01 and
   TC-COMPAT-03-03 both depend on this permission actually being assignable in **Administration →
   Roles and permissions** — confirm that first if either case unexpectedly 403s for a role that
   should have access.
