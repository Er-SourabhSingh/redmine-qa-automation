# Plugin Memory — Redmineflux Gantt Chart

> Plugin-specific observations only. Global rules live in root MEMORY.md.

## Known Quirks

- The "Flux Gantt-Diagramm" project module is NOT enabled by default on any fresh Forge server, even on a project seemingly built for it ("Flux Gantt Project") — always check/enable it at Project Settings > Modules before testing.
- Dependency-link connector handles (the hover-revealed "Eingehende/Ausgehende Abhängigkeit erstellen" buttons) look like normal `<button>` elements but clicking one does NOT start linking mode by itself — a real `page.mouse` down/move/up drag sequence from one bar's outgoing handle to another bar's incoming handle is required (same technique as bar-resizing). `dispatchEvent` synthetic events and a plain `.click()` both do nothing.
- The Gantt grid's DOM is virtualized/dynamically reflowed — a `querySelectorAll` text search can return stale/wrong results if the grid just re-rendered; prefer re-querying immediately before acting, and cross-check with a screenshot when a result looks surprising (e.g. a header that "disappears" from one query but is actually just off in a different render pass).
- A release/version row's "N issues" count and its child rows in the Flux Gantt tree are filtered to the currently-selected Date From/To range, not the release's total issue count. A version whose assigned issues fall outside the visible window will show fewer issues (even "0 issues") — this is by design, not `BUG-GNT-004`'s old under-reporting bug (that was root-caused and fixed on 2026-09-08/09). Cross-check against core Redmine's own Roadmap page (`/versions/<id>`, real total) before suspecting a regression.
- Neither the `Developer` nor `Reporter` role has "View Flux Gantt" / "View Global Flux Gantt" checked by default on a fresh instance (confirmed on the `localhost:3010` local dev build, 2026-09-23) — grant them explicitly at Administration > Roles before any permission-based Gantt test needs a non-Manager role.
- The dependency-connector drag technique (`page.mouse.move/down/up`, not `dispatchEvent`) also applies to the date-range picker's calendar cells — a `browser_evaluate`-driven `.click()` on a calendar `<td>` silently fails to register with the picker's internal state (Apply submits the unchanged previous range) even though the cell visually appears selected; use real `browser_click`/`browser_select_option` with a fresh snapshot ref for every step of a custom date-range selection.
- New per-#120913 CSS classes worth knowing for evidence-gathering (avoid relying on a cropped screenshot alone to judge critical-path highlighting — verify via these classes/computed styles instead): `rf-gantt-bar--critical` (issue bar is on the highlighted chain), `rf-gantt-bar--critical-external` (its incoming critical dependency originates in a different release), `rf-gantt-link-path--cross-release` on the SVG `<path>` (computed `stroke-dasharray: 7px, 4px` vs `none` for a same-release critical link). The cross-release tooltip text format is exactly `"Critical — driven by #<id> <subject> (<release name>)"`.
- The Custom Range date-picker popup (opened via Date From/To → Custom Range) previously did not reposition/flip or cap its own height when there wasn't enough vertical room below. A **bare** 1280×720 content viewport (e.g. a raw Playwright resize) has room to spare, but a **real** 1280×720 browser window (tab bar + address bar + OS taskbar chrome eating into that 720px) does not — reproduce/retest this class of "cut off at 1280×720" report by testing at a reduced content height (e.g. 1280×580) rather than a literal 1280×720 Playwright viewport, or the bug won't show up either way. **Fixed 2026-09-24** (`BUG-GNT-008`, closed): the popup now caps its own height with an internal scroll region (visible scrollbar on the popup's own right edge), so Cancel/Apply stay reachable regardless of available page height.
- The left panel's resize splitter (`.rf-gantt-panel-splitter__grip`) is React-state-driven — a raw `element.style.width` mutation via `browser_evaluate` gets silently stomped back on the next render. Use a real `page.mouse.move/down/move.../up` drag sequence (via `browser_run_code_unsafe`) on the grip to actually resize the panel, same lesson as the dependency-connector and date-picker-calendar drag techniques already noted here.
- Custom-field column headers (`.rf-gantt-left__col-cf`) previously declared `overflow:hidden`/`text-overflow:ellipsis`/a `title` tooltip, same as the already-fixed `BUG-GNT-002` headers, but the ellipsis did **not** actually render once enough columns were enabled to exceed the resized panel width — text hard-cut mid-word with zero "…" (confirmed via a zoomed screenshot crop, not just a compressed read). **Fixed 2026-09-24** (`BUG-GNT-009`, closed): headers now show genuine ellipsis dots; `scrollWidth === clientWidth` for the checked columns post-fix, suggesting the columns were also widened/reflowed, not just given working ellipsis CSS.
- The Settings panel was restructured in the 2026-09-24 rebuild: "Show Milestone Markers" moved out of the general "Display Fields" list into its own distinct **"Milestone Markers"** section, alongside a new per-project date-field control and a colour-swatch picker (`#7048E8`/`#1098AD`/`#2F9E44`/`#E8590C`/`#C2255C`/`#495057`) — this is likely the "bar colours" control from issue #120913 item 4 that could never be located before. This whole section is now **only visible to users with "Manage versions"** (confirmed absent from Reporter-role `daisy.skye`'s panel entirely, even though her personal-settings sections — Zoom/Display Mode/Sort/Display Fields/Custom Field Columns — are all fully reachable) — a reasonable design given the section now controls a genuinely shared/project-wide value, but worth knowing so a future session doesn't mistake it for a BUG-GNT-006 regression. A similar per-issue colour picker (hex swatch next to Estimated Hours, e.g. `#9ad9ae`) also now appears in the Add Issue dialog.

## Recurring Issues

- None currently open for this plugin — all 9 bugs found to date (001–009) are fixed and closed as of 2026-09-24.
- Historical note (kept for future differential-testing discipline): when BUG-GNT-006/007 were open, the lesson was to use a **differential** check (set different values for two users, not the same value) when testing whether a setting is per-user or shared — a same-value check is inconclusive and would have missed BUG-GNT-007. This remains the correct technique for any future per-user-setting test on this plugin.
- When sorting by a field where a parent issue's own value differs from its children's (e.g. Priority), the parent's top-level position appears influenced by its children's values, not strictly its own — same pattern already seen for Due Date sorting. Not filed as a bug (looks like deliberate "most-urgent-child" grouping), but worth knowing before designing a stricter sort-order assertion.
